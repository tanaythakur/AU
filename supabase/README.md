# Supabase setup (do these once, in order)

The database is **empty** until you do step 2. Nothing in this repo can apply SQL to your project for you
(that needs your database password or a dashboard login), so these are manual, one-time steps.

## 1. `.env` (already corrected for you)

```
VITE_SUPABASE_URL=https://<project-ref>.supabase.co      # Project Settings → API → Project URL
VITE_SUPABASE_ANON_KEY=<anon / publishable key>          # NEVER the service_role / secret key
```

`.env` is git-ignored. The app refuses to start (and shows why) if the URL is the dashboard address or the key is a
service-role key.

## 2. Apply the migrations

Open **Supabase Dashboard → SQL Editor → New query**, then paste and run each file **in this order**, one at a time.
Each should finish with *Success. No rows returned*.

1. `migrations/0001_core_schema.sql`      tables, constraints, double-booking guard
2. `migrations/0002_security_rls.sql`     single-admin gate, Row Level Security, privileges
3. `migrations/0003_business_functions.sql` atomic payment / membership / booking functions
4. `migrations/0004_audit_and_reporting.sql` audit trail + reporting functions
5. `migrations/0005_storage.sql`          private bucket for expense bills

(Or with the CLI: `npx supabase login`, `npx supabase link --project-ref <ref>`, `npx supabase db push`.)

If a file fails, stop and send me the exact error message. Do not skip ahead.

## 3. Create the one admin account

Only emails on an allow-list can ever become users, so strangers cannot sign up even if the dashboard toggle is on.

1. SQL Editor → run (use your real email, lower-case):
   ```sql
   insert into public.admin_allowlist (email) values ('you@example.com');
   ```
2. **Authentication → Users → Add user → Create new user**: same email, a strong password, tick **Auto Confirm User**.
   (A trigger gives that user the `admin` profile automatically.)
3. If you had already created that user *before* running the migrations, run this once instead of step 2:
   ```sql
   insert into public.profiles (id, email, full_name, role)
   select id, lower(email), 'Academy Admin', 'admin' from auth.users where lower(email) = 'you@example.com'
   on conflict (id) do nothing;
   ```

## 4. Turn off public sign-ups (defence in depth)

**Authentication → Sign In / Providers → Email → "Allow new users to sign up" = OFF.**
Also keep **Confirm email** ON for any future user.

## 5. Check it worked

```
node scripts/verify-live.mjs                                   # anonymous checks, no password needed
TEST_ADMIN_EMAIL=you@example.com TEST_ADMIN_PASSWORD=... node scripts/verify-live.mjs   # + signed-in, read-only checks
```

The script never writes payments (they are permanent by design) and never creates users.

## 5b. Deploy the server-side Excel export (recommended)

The Excel file is generated by an Edge Function so it uses the database's own numbers and is audit-logged on the server.

```
npx supabase login
npx supabase functions deploy export-accounts --project-ref <ref>
```

No secrets are needed. Until it is deployed the app still exports, but builds the file in the browser and says so.

## 6. Run the app

```
npm run dev
```

Sign in with the admin email and password. Then set your **UPI ID, hourly rate and opening hours** in Settings and
add your membership plans there — there is no sample data any more.

## Operating notes

* **Change the admin password:** Dashboard → Authentication → Users → the user → *Send password recovery* or set a new one.
* **Replace the admin:** delete the old row in `public.profiles` and `public.admin_allowlist`, then repeat step 3.
* **Payments are never deleted or edited.** A refund is a status change with a date. Memberships are never edited;
  a renewal is a new row. The audit log cannot be changed from the app.
* **Backups:** enable daily backups / Point-in-Time Recovery in the Supabase dashboard for real money data.
* **Time zone:** business dates are Asia/Kolkata days, computed in the database.
